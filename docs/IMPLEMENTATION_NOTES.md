# Tasko.ai — реалізація бекенду

## Модулі

Auth — реєстрація, вхід, JWT. Projects — проєкти, учасники, пошук фрилансерів.
Tasks — завдання та замовлення. Collaboration — повідомлення, файли, здача і перевірка роботи.
Admin — користувачі, ролі, блокування, звіт. Analytics — прогрес, дедлайни, ризики, навантаження.
Agent — AI-помічник та MCP. Config, Prisma, Health — конфігурація й БД.

Контролери отримують HTTP-параметри; DTO перевіряють вхідні дані; сервіси містять бізнес-логіку та доступ. ProjectsService перевіряє участь і власника.

## База даних

Збережено наявну Prisma 8 RC. Вісім таблиць: User, Project, ProjectMember, Task, Order, Message, FileAttachment, WorkSubmission.

Додано nullable FileAttachment.submissionId з індексом і зовнішнім ключем. Приймання й статус завдання змінюються в транзакції.

TimestamptzJsDate повертає JavaScript Date. Цей кодек не змінює SQL-типи; окрема міграція фіксує контракт без операцій над даними.

Наявну локальну схему зареєстровано як початкову й застосовано подальші зміни. Дані не очищалися.

## Безпека й помилки

Публічні ролі — CLIENT, FREELANCER; ADMIN створюють окремо. JWT містить ID; актуальна роль і стан читаються з БД.

401 — неправильний токен/вхід; 403 — недостатньо прав або блокування; 400 — некоректні дані; 404 — запис відсутній; 409 — дубль або недопустимий стан; 503 — недоступність БД/AI. Внутрішні помилки не повертають клієнту секрети.

Файли обмежено 10 МБ; перевірено розширення й початкові байти. Це не антивірусна перевірка. Шлях генерує сервер; скачування перевіряє участь.

## AI

Офіційний MCP SDK, JSON-RPC, Streamable HTTP. Інструменти лише читають доступні користувачу дані. AI викликає їх через MCP-клієнт. Додаткові поля провайдера збережено для сумісності tool calls. Є таймаут і ліміт кроків.

## Перевірка та межі

Модульні тести, HTTP-тести авторизації, наскрізний сценарій на справжній PostgreSQL із відкотом власних записів. Перевірено процес роботи, права, некоректні дані, повторні операції, блокування JWT, файли й MCP.

Етап початкового фронтенду описано нижче. Фінальні клієнтські сторінки та їх перевірки наведено наприкінці документа. Навантажувальні тести й одночасні запити не перевірено.

## Відновлення середовища та перевірка AI — 16.10.2026

Причина недоступності БД: Docker Desktop не працював, наявний `taskoai-postgres` був зупинений. Запущено Docker Desktop і цей контейнер зі збереженим томом. Порт — `127.0.0.1:5434`. `prisma db verify` підтвердила відповідність БД контракту без зміни схеми й застосування міграцій.

Причина помилки AI: Groq повертав 404 `model_not_found` для `llama-3.3-70b-versatile`. Список `/models` підтвердив доступну `openai/gpt-oss-20b`; після короткої перевірки змінено лише `OPENAI_MODEL` у локальному `.env`. Ключ не змінювався й не потрапляє в Git.

У `apps/api/test/database.integration.mjs` додано необов'язковий `--live-ai`. Типовий тест не звертається до провайдера. У живому режимі APP_CONFIG використовує справжні AI-налаштування, але JWT і записи залишаються ізольованими тестовими. Перевірка викликає `/agent/chat` як фрилансер, очікує виклик `get_project_summary` і правильний прогрес 100%. MCP читає реальну PostgreSQL всередині тестової транзакції. Усі записи відкочуються навіть у разі помилки.

`apps/api/package.json`: команда `test:ai` збирає API й запускає цей сценарій. Залежності не додавалися; бізнес-логіка й Prisma-контракт залишилися без змін.

Жива перевірка пройшла: 67 HTTP-перевірок, включно з API → Groq → MCP → PostgreSQL → відповідь. Підтверджено відкіт тестових записів. Це підтверджує перевірений сценарій; якість усіх можливих відповідей моделі цим не гарантується.

Після завершення змін повторно пройшли: збірка NestJS, TypeScript, лінтер, Prettier для змінених файлів, 39 модульних тестів і 6 HTTP-тестів авторизації. Типовий сценарій без зовнішнього AI також пройшов 65 HTTP-перевірок із відкотом даних. Попередження vite-tsconfig-paths про вбудовану підтримку Vite не завадило тестам.

Читанням системного каталогу БД підтверджено 14 зовнішніх ключів. Окремий запит не знайшов замовлень із відсутнім клієнтом/проєктом або клієнтом, відмінним від власника проєкту. `Order.clientId` поки перевіряється прикладною логікою, окремого FK на User немає; зміна схеми на цьому етапі не виконувалася.

Запуск і ручний сценарій Swagger — у README.md.

Аудит runtime-залежностей знайшов 2 high advisories у транзитивних hono та @hono/node-server. Оновлення цих залежностей варто виконати окремо перед публічним розгортанням; автоматичний audit fix не застосовувався.

## Початковий фронтенд — авторизація та Layout

Використано React 19.3.1, React Router 8.4.0, Vite 8.3.4, TypeScript 6.0.2. React і Vite встановлено разом із типовими пакетами DOM, React plugin та деклараціями типів. Redux, UI-бібліотеки й Tailwind не додавалися. Оформлення — звичайний CSS.

Основні файли:

- `apps/web/vite.config.ts`: локальний сервер на 127.0.0.1:5173, строгий порт, проксі `/api` до наявного NestJS. Це префікс фронтенду; бекенд не змінювався.
- `src/api.ts`: `request<T>` передає GET/POST/PATCH/PUT/DELETE, JSON або FormData, JWT і таймаут 15 секунд. `ApiError` зберігає HTTP-статус. Звичайний 403 не завершує сеанс; 401 або блокування користувача викликають подію завершення сеансу.
- `src/auth.tsx`: AuthProvider, `login`, `logout` та відновлення через `/auth/me`. Зберігається лише JWT у sessionStorage, а не пароль. Після перезавантаження дані користувача знову запитуються з API. При мережевому збої доступ до робочого простору не відкривається, але токен зберігається для повторної спроби.
- `src/App.tsx`: маршрути `/login`, `/register`, `/`; ProtectedRoute і GuestRoute, екран перевірки сеансу, помилка з повторною спробою, сторінка невідомого маршруту.
- `src/pages/LoginPage.tsx`: справжній `/auth/login`, відображення помилок, блокування форми під час запиту.
- `src/pages/RegisterPage.tsx`: вибір CLIENT/FREELANCER, повторення пароля, справжній `/auth/register`, перехід до входу після створення користувача.
- `src/components/PasswordInput.tsx`: показ і приховування пароля; спільний компонент для двох форм.
- `src/components/AuthLayout.tsx`, `Layout.tsx`, `src/styles.css`: публічна шапка, бічна навігація, верхня панель, мобільне меню. Орієнтир — макети 2.6 і 2.7 з записки; декоративні приклади даних з макета не копіювалися.
- `src/pages/WorkspacePage.tsx`: справжні ім'я, пошта та роль поточного користувача. Це початковий робочий простір, ще не Dashboard зі статистикою.
- `test/api.test.mjs`: 10 ізольованих тестів запитів, JWT, FormData, 204, помилок мережі й відповідей. Використовується вбудований Node test runner, додаткова тестова бібліотека не встановлювалася.
- `test/auth.browser.js`: повторюваний сценарій для наявного Playwright CLI. Реєстрація, помилка повторення пароля, перемикання ролей, неправильний вхід, успішний вхід, оновлення сторінки, втрата з'єднання та повторна спроба, хибний JWT, вихід, 404, повторна пошта та ширина 390 px.

Браузерний сценарій пройшов на справжньому API й PostgreSQL. Створено один тестовий обліковий запис, який залишено в БД; наявні записи не видалялися. Втрата мережі симулювалася лише для `/auth/me` в ізольованому тестовому браузері, а позитивні сценарії виконувалися через реальний сервер.

Перша перевірка збірки, 10 тестів API-клієнта й перевірка типів пройшли. npm audit під час встановлення фронтенду: 0 відомих вразливостей. Лінтер виявив неврахований Promise навігації після реєстрації; додано `await navigate(...)`, без зміни поведінки форми.

Фінальна перевірка етапу: TypeScript, production-збірка, Prettier та Oxlint для фронтенду пройшли; повторно пройшли всі 10 тестів API-клієнта й 39 модульних тестів бекенду. Тимчасовий Vite preview віддав `/login` і `/register` зі статусом 200; `/api/health` через preview-проксі повернув 200 від справжнього бекенду. Після перевірки preview закрито; основні Vite і NestJS залишено запущеними. Помилки HealthController у виводі модульних тестів очікувані: тести окремо перевіряють недоступність БД через підставлений сервіс.

На момент завершення початкового етапу ще не було головної панелі та списку проєктів — їх реалізацію описано нижче. Вихід локальний; серверний JWT діє до завершення терміну або блокування користувача. Для статичного розгортання потрібні налаштування API та SPA-маршрутів.

## Головна панель та список проєктів — 17.10.2026

Орієнтир — опис інтерфейсу в підрозділі 2.1 та макет 2.7 наявної пояснювальної записки. Збережено структуру: чотири показники, таблиця активних проєктів, розподіл завдань і дедлайни. Значення беруться лише з API; приклади назв і цифр із макета не копіювалися. Подальші шаблонні згадки Android/Firebase не використовуються як вимоги до вебзастосунку.

`src/pages/DashboardPage.tsx` паралельно запитує `/analytics/dashboard`, `/projects?status=ACTIVE&limit=5` і `/analytics/deadlines`. Відображає активні проєкти, кількість завдань, завдання у процесі, найближчий майбутній дедлайн і прострочення. Дані не показуються до завершення завантаження; при помилці доступна повторна спроба. Cleanup ефекту скасовує запити та не дозволяє застарілій відповіді змінювати стан.

`src/pages/ProjectsPage.tsx` показує список із сервера, фільтр статусу та пагінацію по 10 записів. URLSearchParams зберігає вибір при перезавантаженні й переходах назад. Некоректні номери сторінок обмежуються безпечним значенням; фільтр скидає сторінку до першої. Загальна кількість не вигадується: API повертає масив, тому після повної останньої сторінки наступна може бути порожньою.

Спільний `src/components/ProjectsTable.tsx` показує назву, розгортаний опис, статус, виконані/всі завдання, прогрес і дедлайн. На мобільному є горизонтальне прокручування та підказка. `LoadError.tsx` уніфікує повідомлення про помилки й повторну спробу. `src/format.ts` містить форматування дат українською та перевірку номера сторінки. Типи відповідей додано до `src/types.ts`.

У `src/App.tsx` головний маршрут тепер відкриває DashboardPage; список — `/projects`, попередню WorkspacePage з даними облікового запису збережено на `/profile`. У Layout додано відповідні робочі посилання. Редагування профілю не додавалося.

Мінімальні доповнення API:

- `projects.dto.ts`: ProjectQueryDto із необов'язковим перевіреним статусом. ProjectsController передає його до сервісу.
- `ProjectsService.list`: спочатку застосовує роль, статус і пагінацію; потім одним додатковим запитом отримує статуси завдань лише для вибраних проєктів. Додає totalTasks, completedTasks і progress. Загальний формат масиву збережено. Спільний getProgress використовується також у detail.
- `AnalyticsService.dashboard`: поле nearestDeadline. Функція nearestDeadline одним проходом знаходить найближчий непрострочений дедлайн незавершеного завдання або повертає null. Прострочення не маскуються найближчим майбутнім терміном.

Схема БД, міграції й залежності не змінювалися. Рольові перевірки збережено; передавання іншого статусу не розширює доступ до проєктів.

Додано 2 модульні тести найближчого дедлайну: спочатку обидва не проходили через відсутність функції, після реалізації перевіряють завершені/прострочені/недатовані завдання, порожній список і вибір найранішої майбутньої дати. До frontend-тестів додано перевірки номера сторінки та дат — загалом 12 тестів.

Наскрізна перевірка PostgreSQL пройшла 76 HTTP-перевірок із повним відкотом своїх записів. Додатково перевіряються фільтрація, лічильники прогресу до й після приймання роботи, найближчий дедлайн, ізоляція користувачів та сторінки списку.

Браузерні сценарії `auth.browser.js` і `dashboard.browser.js` пройшли на реальному API: авторизація після зміни маршрутів, статистика клієнта/фрилансера, приховування приватного проєкту, фільтр і його збереження, порожня сторінка, мережевий збій і повторна спроба, ширина 390 px. За ці два запуски створено 3 окремі тестові облікові записи, 2 проєкти, 1 завдання й участь фрилансера; їх залишено без видалення наявних даних. Позитивні відповіді API не підмінялися.

Межі на момент завершення цього етапу: форми створення/редагування проєкту, детальна сторінка за макетом 2.8 та інші робочі сторінки ще не були реалізовані. Продовження описано нижче.

Фінальні перевірки цього етапу: збірки API та фронтенду, TypeScript бекенду (типи фронтенду перевіряє також його build), Oxlint обох частин і Prettier пройшли. Пройшли 41 модульний тест бекенду, 6 HTTP-тестів авторизації, 12 frontend-тестів і 76 HTTP-перевірок PostgreSQL. Тимчасовий production preview підтвердив маршрути `/`, `/projects`, `/profile` і зв'язок `/api/health` зі справжньою БД; preview після перевірки закрито. Основні API та Vite залишено запущеними. Живий AI повторно не викликався: його інтеграція не змінювалася, а MCP входить до HTTP-сценарію та модульних тестів.

## Створення, редагування й деталі проєкту — 17.10.2026

`apps/web/src/pages/ProjectFormPage.tsx` містить сторінку та спільну форму створення/редагування. Сторінка завантажує наявний проєкт через GET `/projects/:id`, перевіряє роль і стан, а компонент ProjectForm зберігає поля через POST `/projects` або PATCH `/projects/:id`. Після успішного запиту відкривається детальна сторінка. Назва перевіряється після trim; під час запиту форма заблокована, помилка не стирає введені дані. Сервер остаточно перевіряє права, строки й можливість завершення.

Новий проєкт створює лише CLIENT зі статусом PLANNING. Власник або ADMIN може змінити відкритий проєкт. При виборі COMPLETED/CANCELLED показано попередження про заборону подальшого редагування. Закритий проєкт не відкриває форму навіть за прямим URL. Спроба завершення з відкритими завданнями/замовленнями показує фактичну помилку API.

`toDateTimeInput` у `src/format.ts` переводить ISO-дату в місцеві компоненти datetime-local без підміни часового поясу. Змінене значення перетворюється назад через Date.toISOString(); очищене надсилається як null. Незмінений дедлайн не включається в PATCH, що зберігає секунди та мілісекунди початкового значення. Підписи textarea та select відокремлено від самих полів, щоб значення не потрапляли в текст підпису.

`src/pages/ProjectDetailsPage.tsx` відповідає реалізованій частині макета 2.8: назва, опис, статус, дедлайн, кількість фрилансерів, прогрес, таблиця завдань та список учасників. GET проєкту, учасників і завдань виконуються паралельно, скасовуються при переході та не оновлюють стан застарілою відповіддю. Є завантаження, помилки, повторна спроба, порожній список і серверні фільтри статусу/пріоритету. URL зберігає фільтри й сторінку; максимум 10 завдань за запит. Загальна кількість у проєкті береться з його прогресу, а не видається за кількість відфільтрованих записів. Кількість фрилансерів не включає клієнта-власника. Окремі ширини п'яти стовпців не залежать від чотириставпцевої таблиці списку проєктів.

`src/App.tsx` додає захищені `/projects/new`, `/projects/:id`, `/projects/:id/edit`. ProjectsTable містить посилання в назвах, ProjectsPage — кнопку створення лише для клієнта. Типи ProjectMember/Task і українські назви пріоритетів доповнюють `src/types.ts`. Стилі використовують наявний світлий Layout без нових бібліотек.

Перевірено: 13 frontend-тестів (додано перевірку місцевої дати взимку/влітку й секунд), 41 модульний тест API та 6 HTTP-тестів авторизації. ## Фінальна клієнтська частина — 18.10.2026

Реалізовано завершений робочий цикл Tasko.ai. `TasksPage` показує доступні завдання з фільтрами проєкту, статусу та пріоритету. `TaskFormPage` створює й редагує завдання, а `TaskDetailsPage` керує початком роботи, файлами, здачами, поверненням на доопрацювання та прийманням результату. Остаточні переходи статусів завжди перевіряє бекенд.

`MessagesPage` працює зі справжніми повідомленнями учасників. `FilesPage` завантажує й скачує захищені JWT файли. `OrdersPage` реалізує створення, початок, завершення та скасування замовлень. `AiAssistantPage` показує стан налаштування агента, надсилає запити до `/agent/chat` і відображає використані MCP-джерела. `AdminPage` дозволяє адміністратору фільтрувати користувачів, змінювати роль і стан та переглядати реальний звіт.

Спільний `useApi` обробляє завантаження, помилку, повторний запит і скасування застарілого запиту. `ResourceState`, `Pagination`, `ProjectPicker`, `TasksTable` і `FileActions` повторно використовують просту однакову логіку без додаткового менеджера стану. `api.ts` передає JWT, підтримує JSON, `FormData`, бінарне скачування та зрозумілі HTTP-помилки.

Приклад звичайної зміни стану з інтерфейсу:

```ts
await request(`/tasks/${taskId}/status`, {
  method: "PATCH",
  body: { status: "IN_PROGRESS" },
});
```

Клієнт надсилає лише бажану дію. Сервіс NestJS сам читає користувача з JWT, перевіряє його роль, участь, виконавця, стан проєкту й допустимий перехід. Помилка API показується у відповідній формі, а введені дані не очищаються до успішної відповіді.

У бекенді виконано одну локальну зміну: для Multer встановлено `defParamCharset: 'utf8'`. До виправлення українська назва завантаженого файлу пошкоджувалася; інтеграційний тест із `результат.txt` спочатку відтворив помилку, а після зміни підтвердив точне збереження назви. Prisma-контракт, міграції й залежності на фінальному етапі не змінювалися.

Права перевірено для CLIENT, FREELANCER, ADMIN і стороннього користувача. Закриті проєкти доступні для читання, але не для нових повідомлень, файлів, замовлень чи змін завдань. Фрилансер може здати лише власне призначене завдання. Приймає роботу власник проєкту або адміністратор. Блокування користувача робить уже виданий JWT недійсним для наступного запиту.

Після фінального очищення пройшли 40 модульних тестів API, 5 HTTP-тестів авторизації, 15 тестів frontend API-клієнта та 76 HTTP-перевірок зі справжньою PostgreSQL. Зменшення кількості тестів пояснюється видаленням стандартного NestJS `Hello World`, який не належав до Tasko.ai. Пройшли збірки, TypeScript, Oxlint і Prettier. Повний браузерний сценарій перевірив створення проєкту, учасника, завдання, повідомлення, файли, замовлення, два цикли здачі роботи, завершення, заборони доступу, адміністратора та ширину 390 px. ## Дедлайн проєкту та демонстраційні дані — 19.10.2026

`ProjectsService` відхиляє створення проєкту або зміну його дедлайну, якщо дата
не розпізнана чи не є пізнішою за поточний час. Перевірка виконується на сервері,
тому її не можна обійти прямим API-запитом. Якщо старий проєкт уже прострочений,
власник може змінювати інші поля без повторного надсилання дедлайну. Очищення
необов'язкового дедлайну значенням `null` дозволено.

`ProjectFormPage` задає мінімальне значення для нового дедлайну, показує
українське повідомлення та повторює перевірку перед API-запитом. Після виправлення
дати помилка очищується, а форма знову може бути надіслана. Незмінений старий
дедлайн у формі редагування не блокує зміну інших полів.

`scripts/seed-demo.mjs` створює демонстраційний набір однією транзакцією:
2 клієнтів, 3 фрилансерів, адміністратора, 5 проєктів, 12 завдань, 5 учасників,
6 заявок, 4 замовлення, 6 повідомлень, 8 здач робіт і 2 відгуки. Паролі
хешуються наявним `scrypt`. Випадковий пароль і адреси входу записуються в
ігнорований Git файл `.tmp/demo-accounts.json`; секрет не виводиться в термінал.
Скрипт працює лише з локальною БД, використовує стабільні UUID, не оновлює і не
видаляє наявні записи та при повторному запуску не створює дублікати.

Перевірено 76 модульних тестів API, 6 HTTP e2e-тестів, 21 frontend-тест і
116 інтеграційних HTTP-перевірок зі справжньою PostgreSQL. Інтеграційний сценарій
перевірив створення та редагування з минулою датою й незмінність запису після
відмови. Пройшли TypeScript, Oxlint, Prettier та production-збірки. Усі шість
демонстраційних облікових записів успішно пройшли вхід; права на проєкти
перевірено для клієнта, фрилансера, стороннього користувача й адміністратора.

## Підтвердження пошти та Gmail SMTP — 22.10.2026

- Додано Nodemailer, серверні параметри SMTP та одноразове підтвердження пошти.
  Нові користувачі при ввімкненому `EMAIL_VERIFICATION_REQUIRED` отримують
  `emailVerifiedAt=null`; вхід і відновлення сеансу до підтвердження заборонені.
- Міграція `20261022T0752_email_verification` додає поле й таблицю токенів.
  Значення за замовчуванням зберігає доступ уже наявних користувачів.
  Міграцію застосовано до контейнера `taskoai-postgres`; `db:verify` пройшов.
- Токени: 32 випадкові байти, у БД лише SHA-256, строк 24 години, одноразове
  споживання в транзакції з блокуванням рядка користувача. Новий лист скасовує
  попередні токени. Повторне надсилання обмежене хвилиною на користувача.
- Реєстрація, підтвердження та повторний лист мають ліміт 10 запитів/15 хвилин
  на IP і метод контролера в межах одного процесу API. Виправлено обхід через
  варіанти регістру URL та завершальний слеш; додано регресійні перевірки.
- SMTP використовує TLS, таймаути, текстові листи та приховує внутрішні помилки
  провайдера. Після помилки доставки акаунт залишається непідтвердженим, а форма
  пропонує повторний лист. Resend збережено для відновлення пароля без SMTP.
- `/verify-email` доступний без входу; підтвердження виконується явною кнопкою,
  токен прибирається з адресного рядка. Додано `no-referrer`, повторний лист,
  відлік паузи, українські/англійські тексти та інтеграцію з реєстрацією/входом.
- Обхід помилки glob-розпізнавання дужок у Windows-шляху Prisma 8 RC реалізовано
  в `prisma.config.ts` через явне завантаження єдиного файлу схеми.
- Пройшли 126 API unit-тестів, TypeScript API/web, API/web production build,

  одноразовість, зберігання хешу, cooldown і вхід після підтвердження на PostgreSQL
